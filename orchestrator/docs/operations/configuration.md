## Configuration

Every variable below is read by the orchestrator's code or its image. A value the orchestrator does
not recognise, in a variable that takes a fixed set, stops it at start instead of falling
back to something weaker.

| Variable | Default | Meaning |
|---|---|---|
| `ORCHESTRATOR_DATA_DIR` | `data` (`/data` in the image) | Mirrors, task directories and the SQLite database. One orchestrator process holds it at a time: a second one started on it, for the same tenant or another, stops before it touches anything, so each orchestrator gets its own. On Postgres the database holds the tenant the same way: a second orchestrator of a tenant that already has one stops, whatever its data directory |
| `ORCHESTRATOR_CONFIG` | none (`/data/demo/orchestrator.json` in the image under `ORCHESTRATOR_DEMO=1`) | The repositories to connect at start |
| `ORCHESTRATOR_INTERNAL_FORGE_HOSTS` | none | Hosts (`host` or `host:port`, comma-separated) inside the orchestrator's network that a repository connected from the screen is fetched from, such as a GitLab on the company network. Without it, an address that resolves to this machine, a private network or a cloud's metadata service is refused |
| `ORCHESTRATOR_LOCAL_REPOS_ROOT` | none | The folder under which an owner or an admin connects a repository by path from the screen; an orchestrator serving several orgs reads each org's under `<folder>/<tenant>`. Without it no path is connected from the screen |
| `ORCHESTRATOR_PORT` | `8080` | Listening port |
| `ORCHESTRATOR_HOST` | `127.0.0.1` (`0.0.0.0` in the image) | Listening address |
| `ORCHESTRATOR_WEB_ROOT` | `dist/web` | Where the built screens are served from |
| `ORCHESTRATOR_DEMO` | `0` (`1` in compose) | `1` seeds the stand-in repositories once per volume (image entrypoint), offers the stand-in agent, and starts one example task |
| `ORCHESTRATOR_TASK_PROFILE` | `personal` on a `local` orchestrator with process isolation, `isolated` elsewhere | `personal` starts the agent with the person's own Claude Code setup: settings, memory, skills, plugins, hooks and MCP servers, behind the orchestrator's guard (Run as me); `isolated` gives it a profile of its own. `personal` needs process isolation and an orchestrator only this machine reaches, with one account; a cloud orchestrator refuses it. Any other value stops the orchestrator |
| `ORCHESTRATOR_SERVER_TASKS` | unset | `1` runs tasks in the orchestrator's own process, or in its containers. Unset, a team's or the cloud's orchestrator keeps each task for the starter's connected machine, and the task waits until one takes it; a local orchestrator runs its tasks itself either way. The demo's `docker-compose.yml` sets `1`; `deploy/docker-compose.cloud.yml` passes it through unset, and the `.env` examples under `deploy/` carry it as a commented line |
| `ORCHESTRATOR_1PASSWORD_VAULTS` | unset | The 1Password vaults, by name and comma-separated, a task secret's `op://` reference reads from; a reference to any other vault is refused when it is written. Unset, the Task secrets screen offers no 1Password choice |
| `OP_SERVICE_ACCOUNT_TOKEN` | unset | The 1Password service account token the orchestrator's own `op` reads those vaults with; it is handed to `op` alone |
| `ORCHESTRATOR_OP_BIN` | `op` | The 1Password CLI the orchestrator runs |
| `ORCHESTRATOR_MODE` | `local`, or `self-hosted` when any of `ORCHESTRATOR_AUTH`, `ORCHESTRATOR_PUBLIC_URL`, `ORCHESTRATOR_DATABASE_URL`, `ORCHESTRATOR_OIDC_ISSUER`, `ORCHESTRATOR_SETUP_TOKEN` or an `ORCHESTRATOR_SIGN_IN_*` setting is given | `local` is one person's orchestrator on their own machine, with no account and no sign-in screen; `self-hosted` is a team's, with sign-in. `cloud` is an orchestrator many organizations reach over the internet: it stops at start, naming every one missing, without `ORCHESTRATOR_DATABASE_URL` (Postgres), `ORCHESTRATOR_SECRET_KEY` (the same key on every node), an `https://` `ORCHESTRATOR_PUBLIC_URL`, `ORCHESTRATOR_AUTH` other than `dev-admin` and `ORCHESTRATOR_TASK_ISOLATION=container`, `ORCHESTRATOR_TASK_NETWORK=none` (every task reaches out only through the orchestrator's egress proxy: its model, its repository's allow list and its MCP servers; see [Tasks on a cloud orchestrator](../user/tasks.md#tasks-on-a-cloud-orchestrator)), `ORCHESTRATOR_TASK_USER` as `uid:gid`, both numbers other than 0, and the three `ORCHESTRATOR_QUOTA_*` limits, and refuses `ORCHESTRATOR_TASK_PROFILE=personal`, `ORCHESTRATOR_TASK_ENV_PASS`, `ORCHESTRATOR_LOCAL_REPOS_ROOT` and `ORCHESTRATOR_MCP_LOCAL=1`, which hand one organization the host every organization shares. A cloud orchestrator takes no setup code, no password sign-in and no invitation accepted with a password (each answers 403), prints no setup code, and connects no repository by a path on its machine; people sign up with Google, GitHub or Microsoft and create their own organizations (see [Signing up to a cloud orchestrator](../user/people-and-access.md#signing-up-to-a-cloud-orchestrator)). Any other value stops the orchestrator |
| `ORCHESTRATOR_AUTH` | `local` (`dev-admin` in compose) | `local`: accounts and SSO. `dev-admin`: everyone is one admin, for a demo on one machine. Any other value stops the orchestrator |
| `ORCHESTRATOR_SETUP_TOKEN` | a code printed at start | The one-time code that creates the first owner while there is none |
| `ORCHESTRATOR_SETUP_TOKEN_FILE` | none | A file holding that code instead, read the same way as the client secret's file below |
| `ORCHESTRATOR_PUBLIC_URL` | none | The address people and teammates' machines reach the orchestrator at. `https://` marks the session cookie Secure; SSO needs it for its redirect, and a team is asked to report skill use at it. Behind a proxy that ends TLS, set it, or sign-in sees a foreign origin and refuses |
| `ORCHESTRATOR_ALLOWED_HOSTS` | none (any host) | Host names, comma separated, that the orchestrator answers to; any other `Host` gets 421. Under `dev-admin` only `127.0.0.1`, `localhost` and `[::1]` are answered, whatever this says |
| `ORCHESTRATOR_TRUSTED_PROXY` | none | Addresses, comma separated, of proxies in front of the orchestrator; only their `X-Forwarded-For` names the client that the sign-in limits count |
| `ORCHESTRATOR_SECRET_KEY` | none | 32 bytes, as 64 hex characters or base64 (`openssl rand -base64 32`), that seal forge tokens. Without it no token is stored; a value in another form stops the orchestrator |
| `ORCHESTRATOR_SECRET_KEY_FILE` | none | A file holding the key instead, read the same way as the client secret's file below. Preferred: it keeps the key out of the environment, `docker inspect` and process listings (a task's agent under process isolation runs as the same user and can still read the file) |
| `ORCHESTRATOR_DATABASE_URL` | none (SQLite in `ORCHESTRATOR_DATA_DIR`) | A Postgres URL. The orchestrator holds each org it serves with a session lock on one connection of its own and stops when that connection closes, so the URL reaches Postgres directly or through a pooler in session mode; a pooler in transaction mode hands the lock's session to other clients |
| `ORCHESTRATOR_DATABASE_URL_FILE` | none | A file holding the Postgres URL instead, read the same way as the secret key's file, so the password stays out of the environment and `docker inspect`. `migrate-store` reads it too. Setting both stops the orchestrator |
| `ORCHESTRATOR_BACKUP_HOURS` | none (no copy on a schedule) | Hours between the copies the orchestrator takes of itself while it runs, a whole number from 1 to 8760; another value stops it at start. `SIGUSR2` takes one at any time |
| `ORCHESTRATOR_BACKUP_KEEP` | `7` | How many of those copies are kept, from 1 to 1000; the oldest beyond it are removed |
| `ORCHESTRATOR_BACKUP_DIR` | `backups` in `ORCHESTRATOR_DATA_DIR` | Where the copies, and the copy taken before a schema upgrade, are written |
| `ORCHESTRATOR_ATLASSIAN_MCP_URL` | `https://mcp.atlassian.com/v1/mcp` | The MCP server the Jira card's "Sign in with Atlassian" adds as the person's own: Atlassian's, or a stand-in on this machine |
| `ORCHESTRATOR_CATALOG_LINEAR_URL`, `ORCHESTRATOR_CATALOG_NOTION_URL`, `ORCHESTRATOR_CATALOG_SENTRY_URL` | `https://mcp.linear.app/mcp/readonly`, `https://mcp.notion.com/mcp`, `https://mcp.sentry.dev/mcp` | The MCP server each of the Integrations catalogue's **Sign in with <name>** adds as the person's own: the service's, or a stand-in on this machine |
| `ORCHESTRATOR_MCP_REGISTRY_URL` | none (no registry is read) | An MCP Registry (its `/v0/servers` API) the orchestrator reads servers from, https or plain http to this machine; an address with a credential in it stops the orchestrator. Reads time out after ten seconds and are kept five minutes. An owner approves a server whose namespace checks out (an `io.github.<owner>` name with a repository of that owner, a reversed domain with its remotes on that domain) and which pins to a version; approved servers come first when servers are offered, and reach a team only through a request it merges |
| `ORCHESTRATOR_SYNC_MINUTES` | `10` | How often the orchestrator reads every listed repository again and asks GitLab or GitHub where each of its open requests stands (two at a time, at most 100 a round, the ones asked longest ago first); one round runs at a time, and `0` turns the rounds off. A repository whose `triggerSecretEnv` is set also takes its forge's signed push and merge-request webhooks at `/api/hooks/forge/<repository>`: a push reads it again, a merge or close reads that request; a delivery whose GitLab token or GitHub signature does not hold is refused |
| `ORCHESTRATOR_LOG_FORMAT` | `text` | `json` writes one object a line (`time`, `level`, `msg`) and one line per request with its `requestId`, method, path without the query, status and milliseconds; every request answers its id in `x-request-id`, the one its proxy sent when that is a plain token. In either format an address's password is masked and a line that looks like it holds a secret is withheld |
| `ORCHESTRATOR_METRICS_TOKEN` (or `_FILE`) | none (no metrics) | At least 24 characters. `GET /metrics` with `Authorization: Bearer <token>` answers Prometheus text: the release and schema, requests by method and status with their time, each org's listed repositories by sync state, and failed syncs |
| `ORCHESTRATOR_PG_PASSWORD` | `orchestrator` | Compose only: the password of the `postgres` profile's database |
| `ORCHESTRATOR_OIDC_ISSUER` | none | An OpenID Connect issuer, https (plain http only on this machine). Needs the next two and `ORCHESTRATOR_PUBLIC_URL` |
| `ORCHESTRATOR_OIDC_CLIENT_ID`, `ORCHESTRATOR_OIDC_CLIENT_SECRET` | none | The orchestrator's client at that issuer |
| `ORCHESTRATOR_OIDC_GROUPS_CLAIM` | `groups` | The ID token claim that lists a person's groups, for directory sync |
| `ORCHESTRATOR_SIGN_IN_GOOGLE_CLIENT_ID`, `ORCHESTRATOR_SIGN_IN_GITHUB_CLIENT_ID`, `ORCHESTRATOR_SIGN_IN_MICROSOFT_CLIENT_ID`, each with its `_CLIENT_SECRET` (or `_FILE`) | none (no button for that provider) | A cloud orchestrator's sign-in providers, each registered with `<ORCHESTRATOR_PUBLIC_URL>/api/auth/<google\|github\|microsoft>/callback`. An id without its secret, or without `ORCHESTRATOR_PUBLIC_URL`, stops the orchestrator |
| `ORCHESTRATOR_PRIVACY_URL`, `ORCHESTRATOR_TERMS_URL` | none (signup closed) | The operator's privacy policy and terms of use: https, plain http only on this machine, with no user or password. Shown on the sign-in and signup screens and at the foot of every page; a cloud orchestrator creates no organization until both are set |
| `ORCHESTRATOR_ORGS_PER_IDENTITY_DAY` | `3` | How many organizations one person creates on a cloud orchestrator in a day, a whole number of 1 or more |
| `ORCHESTRATOR_QUOTA_MEMBERS`, `ORCHESTRATOR_QUOTA_TASKS_PER_MONTH`, `ORCHESTRATOR_QUOTA_CONCURRENT_TASKS` | none | Read only under `ORCHESTRATOR_MODE=cloud`, which refuses to start with any left out: each a positive whole number or `unlimited`, the limits a new organization's plan starts with. A limit left out is never read as unlimited |
| `ORCHESTRATOR_FORGE_GITLAB_CLIENT_ID`, `ORCHESTRATOR_FORGE_GITLAB_CLIENT_SECRET` (or `_FILE`) | none (no one-click GitLab) | The GitLab OAuth application the operator registered for this orchestrator, with `<ORCHESTRATOR_PUBLIC_URL>/integrations/forge/callback` as its redirect URI and the `api` scope; registering it: [Registering the GitLab and GitHub apps](forge-apps.md#gitlab-oauth-application). Setting one without the other stops the orchestrator |
| `ORCHESTRATOR_FORGE_GITLAB_URL` | `https://gitlab.com` | The GitLab that application is registered on: https, or plain http on this machine for a stand-in |
| `ORCHESTRATOR_FORGE_GITHUB_APP_ID`, `ORCHESTRATOR_FORGE_GITHUB_APP_SLUG`, `ORCHESTRATOR_FORGE_GITHUB_CLIENT_ID`, `ORCHESTRATOR_FORGE_GITHUB_CLIENT_SECRET` (or `_FILE`), `ORCHESTRATOR_FORGE_GITHUB_PRIVATE_KEY` (or `_FILE`) | none (no one-click GitHub) | The GitHub App the operator registered for this orchestrator: its number, its URL name, its client, and its private key in PEM, with `<ORCHESTRATOR_PUBLIC_URL>/integrations/forge/callback` as its callback URL; registering it: [Registering the GitLab and GitHub apps](forge-apps.md#github-app). Setting some without the rest stops the orchestrator |
| `ORCHESTRATOR_FORGE_GITHUB_WEBHOOK_SECRET` (or `_FILE`) | none | The secret of that app's webhook at `<ORCHESTRATOR_PUBLIC_URL>/api/hooks/github-app`, 16 characters or more; without it every delivery is refused, and a removed app is noticed only at its next token |
| `ORCHESTRATOR_SLACK_CLIENT_ID`, `ORCHESTRATOR_SLACK_CLIENT_SECRET` (or `_FILE`) | none (no Add to Slack) | The Slack app registered once for this orchestrator, with the `incoming-webhook` scope and, as its redirect address, the one the Slack card shows. Slack takes no client that registers itself, unlike Linear, Notion and Sentry. Without both, Slack is connected by pasting a channel's webhook address |
| `ORCHESTRATOR_FORGE_GITHUB_DEVICE_CLIENT_ID`, `ORCHESTRATOR_FORGE_GITLAB_DEVICE_CLIENT_ID` | none (the release may carry one) | The client ID of an OAuth App (GitHub, Device Flow enabled) or an application (GitLab.com, not confidential) registered for one person's sign-in with a one-time code; no secret is used or kept. See [Sign in without the command line tools](forge-apps.md#sign-in-without-the-command-line-tools-two-minutes-once) |
| `ORCHESTRATOR_FORGE_GITHUB_URL` | `https://github.com` | `https://github.com`, or a stand-in on this machine |
| `ORCHESTRATOR_FORGE_GITEA` | unset | `1` offers Gitea (and Forgejo from 1.20) beside GitLab and GitHub where a repository's forge is picked; unset, Gitea shows only for a repository already connected there |
| `ORCHESTRATOR_OIDC_CLIENT_SECRET_FILE` | none | A file holding the client secret instead, the way Docker and Kubernetes secrets arrive; one trailing newline is dropped. Setting both, or naming a missing or empty file, stops the orchestrator |
| `ORCHESTRATOR_GIT_NAME`, `ORCHESTRATOR_GIT_EMAIL` | `TeamHandbook Orchestrator`, `orchestrator@teamhandbook.invalid` | The committer of every orchestrator commit, and the author when no person asked |
| `ORCHESTRATOR_AGENTS` | `claude-code,opencode` (`fake` first under `ORCHESTRATOR_DEMO=1`) | The agents a task can use, comma separated |
| `ORCHESTRATOR_CLAUDE_BIN`, `ORCHESTRATOR_OPENCODE_BIN` | `claude`, `opencode` | The CLI to start |
| `ORCHESTRATOR_OPENCODE_MCP` | `0` | `1` gives OpenCode the repository's allowed MCP tools; see [OpenCode and MCP](../user/tasks.md#opencode-and-mcp) |
| `ORCHESTRATOR_TASK_ENV_PASS` | none | Further host variables every agent sees, comma separated |
| `ORCHESTRATOR_TASK_ISOLATION` | `process` | `process` or `container` |
| `ORCHESTRATOR_TASK_NETWORK` | `open` | `none` cuts the agent off the network; container isolation only |
| `ORCHESTRATOR_TASK_IMAGE` | none (`orchestrator-container-tasks` in the override file) | The image a task runs in; required under `container` |
| `ORCHESTRATOR_TASK_VOLUME` | none (`<project>_orchestrator-data` in the override file) | The Docker volume holding `ORCHESTRATOR_DATA_DIR`, mounted into a task container by subpath; without it the task directory is bind-mounted |
| `ORCHESTRATOR_TASK_USER` | the image's user | `uid:gid` a task container runs as |
| `ORCHESTRATOR_TASK_CONCURRENCY` | `1` | Tasks running at once; the rest wait as `queued`, in the order they were started |
| `ORCHESTRATOR_TASK_TIMEOUT_MINUTES` | `30` | The agent is stopped, with everything it started, after this |
| `ORCHESTRATOR_TASK_TEST_TIMEOUT_MINUTES` | `10` | The same limit for the tests |
| `DOCKER_GID` | `0` | Override file only: the group of the host's Docker socket |

Two health answers, neither behind sign-in: `GET /api/health` says the process answers
(liveness), and `GET /api/health/ready` asks each org's store and answers `{"ready": true}`, or
503 when one does not (readiness). Sent with `Authorization: Bearer <ORCHESTRATOR_METRICS_TOKEN>`, the
readiness answer also gives the release, the schema version, and each org with how many
repositories it lists and how many failed their last sync; without it, a caller learns neither
which orgs the orchestrator serves nor its release. A failing sync does not make the orchestrator unready:
what it read before is still served.

The variables the test suites read are under [Tests](../internals/tests-and-lab.md#tests).
